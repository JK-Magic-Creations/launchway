Roadmap

Where Launchway is going

  1. Launchway is one place to host your code, build it, test it, scan it and deliver it, on servers you control or as a hosted service.
  2. It aims to be complete without being complicated: every task is a guided wizard, every capability is also in the API, the command line, the agent endpoint and Terraform, and the only things it needs are a database and Git.
  3. AI helps where you ask for it and stays off where you do not, and every run, change and approval is a durable record you can audit.

As of 2026-11-21. Items are ordered by value, in milestones marked Now, Next and Later. There are no dates: plans change, and an item moves to Available only when it is merged, tested and documented.

Available today

On the main branch, tested and documented. 31 things.

Pipelines

  • Pipelines as code

    Typed YAML with steps, dependencies, run inputs, outputs passed between steps and loops, kept in Git next to the code they build.

  • Flow control

    Conditions on steps, retries with back-off, lanes that make runs take turns, run timeouts, and re-running from any step with what each step was given.

  • Build caches

    Dependencies kept between runs in the database, with entries a pull request can write but the default branch never reads.

  • Triggers

    Push, pull request (with target-branch filters, and newer pushes cancelling older runs), manual, schedule and webhook.

  • Shared libraries

    Templates and scripts in their own repository, pinned by tag, branch or commit, with typed parameters.

  • Step resources

    Each step is sized, with defaults per kind of step and a ceiling no step can pass, so one step cannot starve a cluster.

Platform

  • Configuration in the database

    Projects, runner pools, environments, policies, models and more are objects in the database with history, audit and safe concurrent edits, never a file to hand-edit.

  • Four levels

    Installation, organisation, unit and project, with names you choose and levels nobody uses kept out of sight.

  • Guided setup wizards

    First-run setup, connecting a repository, adding a runner, an environment, a policy or a verification step: plain questions, explained options, answers checked as you go.

  • A guided interface

    Six sections (Home, Projects, Deployments, Activity, Library, Settings), a Home page that says what to do next, and sections that appear only when there is something to show.

  • One capability, every interface

    What the web UI does, the HTTP API, the command line and the agent endpoint do too, with a table in the build that fails when one falls behind.

  • High availability

    Several servers on one PostgreSQL database with no leader; a run survives a server or a runner dying. SQLite for a single server.

  • Signed releases and installers

    Reproducible, signed release builds with SBOMs and provenance, deb and rpm packages and an install script for runners, and a runner-only Helm chart. The first published release is still to come.

  • Self-deploy

    Launchway builds, tests and deploys itself through its own pipeline, with a way back in when it is down.

  • Quality gates

    Lint, size, architecture, test and originality checks fail the build, so the code stays easy to change.

Delivery

  • GitOps with Argo CD

    Deploy by Git commit, watch sync and health, control Argo Rollouts (promote, abort, retry), roll back, lock environments.

  • Applications view

    The Argo CD applications a deploy runner has seen, shown with their status next to your environments.

  • Verification after a deploy

    Checks on Prometheus, Loki, ClickHouse and OpenSearch with automatic abort or rollback; an optional model explains the verdict and never turns a failure into a pass.

  • Container images

    Rootless builds, scans, signatures, provenance and SBOMs, pushed to any OCI registry.

  • Approvals and protected environments

    Approval steps; the person who started a run cannot approve its production deploy.

Security

  • Policy gates

    Rules pipelines cannot opt out of, at run start, before deploys and image pushes; report or enforce; audited, expiring waivers.

  • Sign-in and access

    OpenID Connect sign-in with groups, roles per project and environment, scoped API tokens and an audit trail.

  • Secrets that stay with runners

    Pipelines hold references; runners read values from Vault, OpenBao, files or the environment, and mask them.

  • Security findings and SBOMs

    Secret, code, dependency, licence and image findings (SARIF), new and fixed across runs, and a component search.

  • Secure step execution

    Non-root step pods under strict pod security; container and host executors; runners only connect outbound.

  • Runner identity and pools

    Join tokens, a key per runner, pools scoped to projects, and allow-lists on the runner itself.

Reports

  • Test, coverage and HTML reports

    Thirteen test formats, coverage with thresholds, flaky-test detection, history, and the tools' own HTML reports in a sandbox.

  • Built-in artifact storage

    Artifacts and hosted reports live in the database by default, so several servers need nothing else; S3 or a shared folder are optional.

AI

  • AI models in steps

    Optional hosted or local models for steps and failure explanations, with per-model token limits; keys never enter a step's container.

  • An endpoint for agents

    Agents validate pipelines, start and watch runs and diagnose failures with exactly the rights of the token they hold.

Project

  • Open source

    Free software under the AGPL-3.0, with a commercial licence for those who cannot use it, and this documentation site with its roadmap.

Throughout, not a milestone

The standard every item is held to.

  • Everything, without the mess

    Every feature uses the same objects, permissions, audit trail and policy point, and nothing switched off appears in the menus.

  • One way in, every way in

    A wizard for each task, with the same operation in the HTTP API, the agent endpoint, the command line and Terraform.

  • Only a database and Git

    Everything else is built in; outside integrations stay optional.

  • Boring upgrades

    One binary and a database, additive migrations, an older binary running on a newer schema, and rollback by image.

  • High availability and security are part of done

    A feature says what happens when a server, the database or a runner dies, and who may do what, before it merges.

  • Honest status

    An item is available only when it is merged, tested and documented. Order is by value and is not a schedule.

Launchway is not certified against any compliance standard; compliance items provide controls and evidence. Nothing here is a commitment to a date. The same items, as a table, are in the roadmap as a list.
